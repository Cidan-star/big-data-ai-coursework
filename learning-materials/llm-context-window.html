1. 个人解释

把大模型的"上下文窗口"想成一个人的"工作记忆容量"：你给模型一段提示词和几段材料，它只能同时"看到"这些内容然后作答；如果再多，它就会把最前面的内容"挤出去"，再也想不起来。

GPT-3 时代这个窗口只有 4K token（约 3000 个汉字），如同你只能给助手看一页纸；GPT-4 Turbo 把窗口扩到 128K，Claude 3 / 3.5 已扩到 200K 到 1M，相当于一次性喂给模型一本小说。窗口越大，模型就越能"全局思考"，但成本和延迟也会显著上升。

2. 核心机制

上下文窗口由四个底层机制共同决定：

2.1 Token 化

LLM 不直接处理字符，而是把文本切成 token（常见做法：BPE、WordPiece）。一个 token ≈ 0.75 个英文单词，或 1–2 个汉字。上下文窗口的"长度"实际指 输入+输出 token 总数。

2.2 自注意力的复杂度

Transformer 的自注意力对长度为 n 的序列计算两两关系矩阵，复杂度 O(n²)。当 n = 100K，attention map 就有 10¹⁰ 项，显存与算力压力剧增。

Memory ≈ 4 · n · d (KV Cache) + n² · h (Attention)   其中 d = head_dim, h = n_heads

2.3 KV Cache 优化

自回归推理时，模型为已生成的每个 token 缓存 Key 与 Value 向量，避免每步重算历史，这就是 KV Cache。它是长窗口推理能"跑得动"的关键工程优化。

2.4 有效上下文 vs 理论上下文

许多号称 200K 窗口的模型，在处理长上下文中的中后段信息时，召回率显著下降——这就是著名的 "Lost in the Middle" 现象。实际可用窗口常常 远小于 厂家声明的窗口。

2.5 关键拓展技术

  • RoPE / ALiBi：相对位置编码，可外推更长序列
  • Sliding Window Attention：限制每 token 只看近邻 k 个（如 Mistral）
  • 稀疏注意力 / FlashAttention：在 O(n²) 内做内存与算力的优化
  • RAG：把"超出窗口"的知识检索后注入到提示词，弥补窗口限制

3. 应用场景

场景上下文扮演的角色简明示例
长文档问答 一次性塞入整份手册，模型基于原文作答 把一份 100 页的招聘法规贴进去，问"试用期内解除的法定情形"
多轮对话 保留历史对话，避免每轮重复告知 持续 50 轮的 debug，模型记得每一步的报错和尝试
代码仓库级理解 喂入整个项目的源码以做全局重构 Cursor / Copilot 把几 MB 的 monorepo 一次性送到 Claude 200K 窗口做 review
RAG 检索增强 把检索到的片段拼成临时上下文 用户问"去年报销流程"，系统先检索 5 段 SOP 填入 context 再让模型回答
长内容生成 一次性产出长文档而无需切段 让模型基于大纲直出 1 万字的研究报告，无需拼接

4. 边界辨析

区分点上下文窗口相邻概念
作用维度 一次推理的输入+输出容量 Token Limit：通常只指输入侧的上限
时间跨度 短时、随请求结束清空 Memory：跨会话持久化的长期记忆
评测对象 窗口大小只是理论上限 有效上下文：模型实际能利用的容量
扩展方式 由模型架构决定，难以临时扩展 RAG：用检索补足，不属于"上下文"本身

4.1 vs Token Limit

上下文窗口指单次请求能放进模型的总 token 数（包括输入和输出）；Token Limit 通常只指输入 prompt 的最大长度。

OpenAI API 文档里的 max_tokens 参数控制的是"模型最终输出长度上限"，与模型本身的上下文窗口是两个独立的参数；混用容易误判模型容量。

4.2 vs Memory（长期记忆）

上下文随请求结束消失；Memory 是工程层外挂的向量数据库、文件或 KV 存储，跨会话保留。

用户输入"我叫小明"，60 轮后模型不会"记得"，因为已超出上下文；但如果工程层把这句持久化进向量库，下次启动新会话时仍能检索到——这就是 Memory。

4.3 vs 有效上下文 (Effective Context)

标注 200K ≠ 能用 200K；模型对中后段信息的精确率常显著低于首段。

Liu et al. (2023, "Lost in the Middle") 实验：把关键事实放在 64K 上下文的中部，模型回答准确率比放在首部/尾部低 30% 以上。
